# Assess quality gaps: where to start

1. Find the quality folder and any saved work, as [where the documents
   live](../../../references/document-home.md) describes.
2. If there is no strategy, the request is one quality question on its own, and the earlier steps
   need not have run. [Where the strategy stands](../../../references/where-things-stand.md) says how
   to tell. Do these in place of the rest of this section, asking only for what the request did not
   say:
   1. Ask what question is to be judged, in the user's words.
   2. Ask how good it must be. If they don't know, record the bar as unknown, with what would
      settle it.
   3. If reading the project is enough to answer, say in the first message what will be read and
      go ahead, because reading is not a check. If it needs more, such as running the tests, ask
      whether they have agreed a way of measuring it. If none, open [plan the
      measurement](../../plan-quality-measurement/SKILL.md) for that one row, and come back with
      the way it planned, as [when one skill opens
      another](../../../references/opening-another-skill.md) says.
   4. Assess that one row as the rest of this skill describes, running or leaving its planned check
      as step 6 says. Where it names the strategy's plan or bar, it means this one.
3. In a strategy, run `status`, as that reference describes.
4. Read the measurement plan, its checks with the rows each answers and the rows it puts in scope,
   and each row's bar. Where the release's bar is still open, read each
   stakeholder's goal named in the row instead, because such a row is judged against each goal
   separately. Read each from its step's notes or, in an older strategy without them, as [the
   records guide](../../../references/quality-model.md#records) says.
5. If a row in scope has no plan at all, get it planned first. Don't fold the planning into the
   measuring, because how to measure is a separate step and comes first.
   - If the user asked to skip that planning, open [drafting steps without the
     user](../../draft-strategy-steps/SKILL.md) for it.
   - Otherwise, with the user here, open [plan the
     measurement](../../plan-quality-measurement/SKILL.md) for it, and come back with the way it
     planned, as when one skill opens another says.
6. Measure by a way the user agreed, or one they saw and left as the agent's, and say in the finding
   which. Put a way they have never seen to them first, because they have had no chance to change
   it.

   Before the first run, read the plan and decide what happens to each planned check, because
   effort is saved only if the agent knows in time what it can leave. Decide from [the measurement
   notes](../../../references/saving-records.md#the-measurement-notes): each check's status, and
   what its pass and fail would show.
   - **Runs:** a `planned` check, including one against no bar, and a check they asked for in order
     to decide, which is never left unrun.
   - **Waits:** a check they said to leave, one `waiting on its bar`, and one that needs an answer
     they have not given. A rating left open holds nothing up.

   Then decide which invocation serves each check that runs. One invocation can serve several checks
   when one check's pass and fail, as the plan records them, are contained in another's, so a
   check served that way gets no invocation of its own. A check they asked for in order to decide
   gets its own.

   After each run, and whenever a planned run is declined or will not be made:
   - Record what it showed for every check it served, naming the invocation, because one run that
     serves two checks is one observation pointed to twice, not two results.
   - A check it was meant to serve but did not reach, because the run was declined, stopped early
     or was not made, still runs. Run it on its own, unless the user declined something it needs as
     well, in which case it is declined with that.
   - Look at the checks still to run. One whose pass and fail are now shown by what has run is left
     unrun, unless they asked for it in order to decide, and the findings name it with what showed
     it. Settling a row's judgment does not show who is affected.

   Nothing is recorded as shown before a run has shown it, because what the findings know is what
   has been seen.
7. Tell the user what the assessment will do, as [a good investigation](what-to-bring.md#a-good-investigation)
   says, including which run serves which checks, and any assumption known to be out of date. Name
   rows by their question as they come up, rather than reading out the list, because a list of row
   numbers means nothing to them. Rows outside the assessment keep their earlier status.
