# Assess quality gaps: while investigating

## A good record

The record is the assessment notes. The strategy's part on where things stand is written from them
for a reader. What a finding holds, and where the evidence behind a run is kept, is in [the
assessment notes](assessment-notes.md).

For each finding, a later reader can tell which question it answers, what it was judged against,
what it rests on and how sure to be, because the plan of work and the release call will be made on
it. A finding that rests on something the agent ran links what was run and what it showed, so that
someone can run it again.

Nothing is concluded that its observations cannot carry, and observations that point the other way
are kept. Findings are saved as they are made, so the work can stop, resume or be handed over.

Each unknown says why it is unknown, because what to do next depends on the reason. The usual
reasons are these:

- nobody has looked;
- what was seen could not settle it;
- nobody knows a way to judge it;
- the bar is unsettled: nobody has said what good looks like.

A bar the user stated is not unsettled because a word in it can be read more than one way. Judge
against their words and quote them, and label your reading of that word as yours, because a bar
put in other words is no longer the one they set.

When the observation has to wait, for the release to be in people's hands, for someone's answer or
for a tool, what it waits on is the reason. Each unknown also says what would settle it and what
that needs. Where the project's files name someone who may know, such as a maintainer, say so as
what the files show, because the user may not know it; how to find out stays the user's to choose.
"Not known" is a true answer.
An investigation invented to make the record look finished is not.

## As each finding is made

Before the first finding is saved, and as each is made:

1. Open [the assessment notes](assessment-notes.md) and follow it for what a finding and its
   evidence folder hold, because it says what to keep so that another session can run the work
   again.
2. Outside a whole strategy, run `comms-prep` before the first draft of a record the user will
   read. In its brief, say what the record is for as [each
   turn](../../../references/strategy-workspace.md#each-turn) says under "What the records are for", because the review works from the
   brief. In a whole strategy the connecting step does this once, at the end.
3. Before the first save, open [where the documents
   live](../../../references/document-home.md#before-the-first-save) and do what it says, because the
   user has to know who can read what is about to be saved.
4. Save each finding as it is made, marked `not yet seen`. In a strategy it goes in the assessment
   notes. For one question outside a whole strategy, it goes in the document the user names, or in
   a finding on its own, as [a result outside a
   strategy](../../../references/writing-your-part.md#a-result-outside-a-strategy) describes. If it
   replaces a saved finding, first do as [revisions](../../../references/revisions.md) says.
5. In a strategy, bring its opening up to date in the same save as each finding, because the
   strategy is read between write-ups and the opening is what a reader sees first:
   - the line on how finished it is says an assessment is under way, with the date;
   - the bottom line is the agent's reading so far, labelled as the agent's and not yet put to the
     strategy owner.

   Where the strategy's part on where things stand already exists, bring it up to date in the same
   save too, as [keeping the
   strategy true](../../../references/writing-your-part.md#keeping-the-strategy-true) says.
   Where it does not, it is first written once the user has answered the findings, as [record and
   close](record-and-close.md) says, because a part written sooner would state
   findings they have not seen as the strategy's.

These hold throughout, because each guards against something that has gone wrong before:

- **Nothing beyond what was asked.** Before a longer look the plan did not name, or any check, do
  as [before a new step, a longer look or a
  check](../../../references/look-and-check.md) says. A finding from a read they did
  not know about has no context for them, and a fetch or a live service is theirs to allow.
  - Where a local build with what is already installed would let a planned check run, say so and
    run it.
  - Where it needs a fetch or an install, make the ask the one question of the message in which
    the need is found. That is usually the first message, the one saying what the assessment will
    do. Ask before putting the findings to them, because the findings message keeps its one
    question for the findings, and they should read the findings once, with the runs in. Until they
    say yes, the reading stands, with the run as the next observation.
    - A yes that an earlier step recorded covered the run it named, so a run this assessment adds
      needs its own yes, in this conversation. The scratch copy is for the run; the finding and its
      evidence still go to the records as [the assessment notes](assessment-notes.md) say, because
      saving there does not touch their checkout.
  - A fix they ask for is a change to the product, which that reference also covers, not part of
    the assessment.
- **A priority that turns out wrong or missing goes to the [Open
  section](../../../references/open-section.md),** for the plan of work to put back to the user. Run on
  its own, ask whether to add it to what is being assessed or keep it there.
- **A check set aside for later** is offered to the user. It goes in the Open section with the
  question it would settle, or in the plan of work once someone takes it on.
