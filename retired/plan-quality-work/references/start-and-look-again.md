# Plan quality work: start from findings, and look at the ratings and bars again

## Start from findings the user has seen

1. Find the quality folder and any saved work, as [where the documents
   live](../../../references/document-home.md) describes.
2. If there is a strategy, run `status`, as [where the strategy
   stands](../../../references/where-things-stand.md) describes; it also says how to tell whether there
   is one. Run on its own with no strategy, this skill records nothing.
3. Take whichever of these is the starting point:
   - **An assessment made in this conversation.** Start once the user has seen what it found and
     what is still unknown, and has replied. If they haven't, tell them, ask what they make of it,
     and stop there: propose no work in the same message as the findings.
   - **A saved assessment or strategy.** Read the findings, from the assessment's record as [the
     records guide](../../../references/quality-model.md#records) says, and reuse what they found,
     saying what needs checking again. Findings marked `not yet seen` go to the user first.
   - **An incident or a concern brought on its own,** outside a whole strategy. Get clear on the
     stakeholder, the release, the outcome wanted and what is known, only as far as the plan
     needs; the earlier steps need not be done.
4. Use [the four questions](../../../references/quality-model.md#four-questions) to find what is
   unknown.

## Look at the ratings and bars again

1. Put each of these back to the user as an open question about what to do, and use what they
   decide to order the work:
   - a bar that may be out of reach;
   - a rating that may no longer fit;
   - a priority the assessment left in the Open section as wrong or missing;
   - a rating or bar whose note, in the user's words, puts it off until a step or an event that
     has now come. [The Open guidance](../../../references/open-section.md#a-question-they-declined-or-parked)
     says to put it to them then, because the answer is theirs. If they still cannot say, the
     question stays open with what it now waits on.
2. Record a changed rating or bar in the priorities table, keeping the earlier value beside it
   with the reason and date. The agent does this here; no separate priorities session is needed.
   In the same save, edit the strategy's parts that state it, as [keeping the strategy
   true](../../../references/writing-your-part.md#keeping-the-strategy-true) says, because the
   strategy is read before the last step and must not state the old value.
3. When it is the bar that changed, mark that row's way of measuring and its finding `judged
   against the earlier bar`.
4. In a strategy, after any such change, record `step priorities done --revised`, so that the steps
   built on the priorities are shown to check, as [revisions](../../../references/revisions.md) says.
5. Then run `status` and deal now with what it lists to check, as [what comes
   next](../../../references/where-things-stand.md#what-comes-next) says, because they are here and
   one answer now saves the next session opening on bookkeeping.
6. Change what the release waits for only if the user says so. A change to what the release
   covers or when it ships goes in the project context.
7. Leave the stakeholder's own goal as it was. When the release now aims lower than their goal,
   that goal is unmet, and goes in the Open section with who accepted it.
