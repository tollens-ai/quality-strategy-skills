# Plan the measurement: making the plan, saving and closing

Opened from [the skill](../SKILL.md) when the discussion of the rows begins, and read on to the end,
because saving and closing follow the user's answer.

## Making the plan

Read [what to bring](what-to-bring.md) before the discussion: ideas that have made measurement plans
better, among them what an oracle is and what a proxy cannot show. Use them where they fit.

### What is already known

Before the plan is drawn, gather what is already known across every row in the table, whatever its
rating or lack of one, because a known fault in a Low or unrated row is found only here:

- **What the user has seen.** Ask once what they have seen of the rows themselves: in their own
  use, in a pass through the product, or from what someone told them. Ask it now, because a row
  someone has already seen needs no measurement, and an answer that came with the whole plan would
  rebuild it. A row nobody has looked at is where the planning matters most.
- **What the records say.** Add what the interview, the context, the profiles and any earlier
  assessment say. A stakeholder's level, such as a Dealbreaker, is what they expect and not
  something that happened, so it is not written as known.
- **The pre-read, read again.** Read the whole of it against every row, not only its summary,
  because its detail was filed before the rows existed. A finding that bears on a row is what is
  known for it, or a case its check must exercise. What a run at the pre-read showed is already
  known for its row, with its evidence, and is not planned again.

Then judge which rows a known fault or a consequential unknown brings in, as [where to
start](where-to-start.md) describes, whatever their rating, and bring them in. Say in one list which
rows you brought in and why, so that a fresh session reads the scope from the record, and because a
row silently dropped and every row worked were both faults.

### What the discussion settles

Besides what [a good plan](../SKILL.md#a-good-plan) holds, the discussion has to settle these:

- **The checks.** Draw the plan as checks, each one thing someone would do, such as one run, one
  read, one conversation or one trial with the release in people's hands, and list the rows each
  answers. Rows that one check can answer share it, because a plan of one entry for each row cost
  the user a long read and was approved without a view. Two rows that need different things to
  happen get a check each. A row in scope because the user named it is in a check like any other,
  without asking them for a rating or a hold first.
- **For each check, an instrument and an oracle:** a way to observe and a way to judge what is
  seen, for each row it answers, as [how would we
  know](../../../references/quality-model.md#four-questions) describes.
  For a bar about a rare failure, such as "never lost", say which ways it could happen a check
  exercises and which it cannot, because a clean run shows little and the user decides what that
  is worth.
- **For a row the release waits for,** how what the release must show will be shown, which may not
  be the bar's own check, because the release call rests on that condition and it is the user's.
- **Rows that wait.** A plan where every row waits on something is still good if each row says what
  it waits on. Don't swap in a check that can run now for one that waits, because a substitute may
  not show what the release needs.
- **Work in its own right.** A measurement that needs something built, access nobody has yet, or
  the release in people's hands is marked as work for the plan of work, because otherwise the plan
  of work finishes without it.
- **Checks beyond the project.** Where a way of checking would touch a live service or someone's
  account, the plan says so, because running it is the user's to allow, as [a
  check](../../../references/look-and-check.md) says.

### Showing the plan

Then show the user the whole plan, with no measurement in it:

- what is already known;
- the checks, each with the rows it answers, what would be looked at and what would count as good
  enough;
- the rows in scope that no check answers, with what would need finding out;
- the rows brought in for a known fault or an unknown, and why;
- the rows not checked before this release, named together with their ratings and questions.

Show it whole, rather than in pieces each asked to stand, because that cost the user turns and told
the agent nothing.

Ask about what only they can give that is still open: which check comes first, whether a check that
touches a live service may run, and a bar that is still unsettled. What they have seen was asked
before the plan was drawn, so it is not asked again. Their reply settles whose each part is, as [the
record of agreement](#the-record-of-agreement) below and [judgments and
labels](../../../references/judgments-and-labels.md#labels) describe.

### When the user doesn't know

Not knowing means different things, and each is handled on its own:

- **How a row should be checked.** The check is the agent's way, labelled as the agent's, and the
  assessment runs it, because how to check something is craft the agent may know better, and
  asking them again hands nothing over. They can object when they see it. For a row in scope that
  nothing has measured and that they cannot size, such as "I don't know what a typical run costs",
  the agent's way is a check that finds out, such as measuring a few runs.
- **How good it must be.** A bar they don't know stays an open question, and the row's judgment
  waits for it. The row still gets a check, the agent's way, that finds out how the product behaves
  there now, judged against what needs no bar: its own claims, how it behaved before, or what a
  reasonable user would expect. Such a check is `planned`; [the measurement
  notes](../../../references/saving-records.md#the-measurement-notes) say when one waits on its bar.
- **A row they have already left until they know more.** Don't ask about it again.

## The record of agreement

The record shows whose each part is:

- What the user answered is theirs, with their words quoted once, and it covers no more than they
  addressed: their hedges and limits stay with it.
- A check they saw and did not address, or one they said they don't know about, stays the agent's,
  marked with when they saw it. The assessment may measure by it under that label, because how to
  check something is craft the agent may know better. A judgment of their own, such as a bar, is
  not used until they give it.
- A check they said to leave, or whose bar they have not given, carries the status [the
  measurement notes](../../../references/saving-records.md#the-measurement-notes) give it, because
  the assessment reads that status to know which checks wait.
- Nothing they did not see is labelled agreed. Detail added after they saw the plan is the agent's,
  and agreeing to a summary is not agreeing to detail it left out.
- If they stop partway, what they have seen and what they have not are plainly different.

## Save

1. Before the first save, open [where the documents
   live](../../../references/document-home.md#before-the-first-save) and do what it says, because the
   user has to know who can read what is about to be saved.
2. If this replaces a plan already saved, first do as [revisions](../../../references/revisions.md)
   says.
3. Save the plan in the measurement notes. For one question outside a whole strategy, save it in
   the document the user names or in a finding on its own, as [a result outside a
   strategy](../../../references/writing-your-part.md#a-result-outside-a-strategy) describes. What
   the notes hold, check by check, is in [the measurement
   notes](../../../references/saving-records.md#the-measurement-notes).
4. In a strategy, write how each priority would be known, check by check, in the strategy's part on
   where things stand, as [writing your
   part](../../../references/writing-your-part.md#writing-your-part-at-a-steps-close) says. That is
   a new part once the user has seen the whole plan and answered, or an existing one updated as the
   notes change. Bring the strategy's opening and its open questions up to date
   too.
5. Once they have seen the whole plan and answered, record `step measurement done`. If they
   stop before that, leave the step unfinished. Leave the checks they have not yet answered as the
   strategy states them, because the notes hold what was done. Run on its own with no strategy,
   this skill records nothing, because there is no strategy to record it in.

## Close

1. In a strategy, run `status`.
2. Open [stopping and coming back](../../../references/stopping-and-returning.md) now, then update
   the progress note and write the closing message as it says.
3. In a strategy, unless they have just said what to do next, wait for their answer to the offer
   that message ends with, because no step starts before the user chose it. Saying which check
   they would start with is an answer to the plan, not that choice: the checks are run by the
   assessment, which starts when they choose it from the offer.
