# Telling the person about the major issues

The pre-read, the project context and drafting without the user all tell the person about the major
issues a pre-read found in this way. Tell them before they decide anything an issue affects,
because a decision made without knowing about a serious fault is one they may not have made.

Tell first the issues that would cost most, and whom, in this project. Lost work or data usually
comes first, because it is what people can least recover from.

- **Tell each issue that could lose work or data, or break what users have, on its own,** in a line
  that says what it could cost whom, such as "the upgrade command writes the new config over any
  existing one and then deletes the old, keeping no backup, so a wrong or half-written conversion
  leaves users nothing to go back to", because a count alone tells them nothing about any of them.
  If there are too many for one message, say so, then give them as a numbered list.
- **The others:** tell them one by one, as many as they can take in and weigh, then give the rest
  as a count and the kinds of issue, and offer to go through them.
- **If there are none,** say so in a clause.

Say which issues were only read in the files and not seen running. If they want one seen running,
run it in a scratch copy as [before a look or a
check](../../../references/before-a-look-or-a-check.md) says, keep what it would take to run it
again and what it showed, as [what is true
now](../../../references/templates/every-document.md#what-is-true-now) says, and record in the
digest that it was seen running only if the run showed the fault.

If they stop before you have told them every major issue, say in the progress note which are still
to tell, because the next session tells them first.
