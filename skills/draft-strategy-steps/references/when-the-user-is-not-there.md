# When the user is not there

Whoever drafts a step reads this first, then the step's own skill. Each step and the pre-read are
run by their own skill, as written, with these differences. They apply only to what is drafted
without the user: a project context the user chooses to do together is done as its own skill says.

- **Questions.** Where the skill asks the user a question, answer it from the project context, what
  the user has said, the interview, the pre-read and the earlier drafts, and say what the answer
  rests on. If nothing supports an answer, write it as a question not yet asked, with what would
  settle it, or, where a guess would help the user review faster, guess and say it is a guess.
- **Waiting.** Where the skill shows the user something and waits, carry on. Where it would ask them
  before doing something, leave that undone and write it in the draft as a question for them,
  because going on without them is right for what the skill would only have shown them, not for
  what it would have asked their permission for.
- **Permission to look further.** Wherever [a longer look or a
  check](../../../references/before-a-look-or-a-check.md) would ask the user first, nobody is there
  to ask, so don't do it, unless the request or the sources in the assignment named that very thing.
  Write what it would have settled as not known, and name it for the hand-back.
- **Depth.** Drafting without the user is not a shorter route: nobody is there to catch what is
  skipped, so it takes more care, not less. Address every step asked for, each with enough
  substance for the decision it informs, and its assumptions and missing evidence in plain view.
  How deep to go is your call from what the sources hold: a view drafted from thin sources is a
  short one that says so, because a long draft of guesses costs the user more to review than it
  gives them.
- **A stakeholder nobody speaks for.** Never record `stakeholder nobody-here`, because that choice
  is the user's alone. Where they said they would rather wait for a stakeholder, draft no view for
  them. Where they said "I'd have to ask", draft that stakeholder's view as for anyone else, but
  as a short account, even when the sources say a lot.
- **What is saved.** Start what the step writes with the line "Drafted by the agent on <date>,
  without the user; not yet reviewed." Mark whose each claim is and where it came from, as the
  template for what the step writes says, so that the user's earlier answers stay theirs. At the end
  of the draft, list briefly the answers that shaped it, where each came from, and the guesses that
  most need checking. Where the step writes into the strategy, say the same once at the head of the
  strategy and once in each priority's section it drafted, because a reader may take a section away
  alone and not see the head.
- **Recording.** Record the step as drafted, never done, because done means the user has seen it and
  answered; the assignment gives the command. A drafted project context also records `release "<the
  release>"` and `stakeholders "<name>" ...` in the draft's order, because the next draft needs
  them; they are the draft's guesses, and the draft says so. Where the skill's **Done when** asks
  that the user has seen and answered something, a draft meets it by being saved, saying it is a
  draft, and being recorded as drafted.
- **Adding to another step's record,** such as a fact added to the project context: say that the
  addition is the agent's, with the date. Leave that record's status as it is, because the user's
  review of the rest of it still stands, and the hand-back names the addition. Record as drafted
  only a record the agent makes, or a step it does again.
- **The close.** Don't send the step's closing message; the hand-back takes its place. A review the
  step runs for its reader, such as the write-up's, still runs, because the user will read what it
  produces.
